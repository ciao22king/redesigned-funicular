## 1. Deploy su Cloudflare Workers

### Situazione di partenza

Il deploy falliva con:

```
An unknown error has occurred
```

Il progetto era già stato migrato da GitHub Actions a **Cloudflare Workers
Builds** (integrazione nativa). Il workflow GitHub era diventato solo CI
(`ci.yml`: `npm ci` + `npm test` + `npm run build`, nessun deploy, nessun
secret).

### Diagnosi

L'errore era **transitorio**: un bug noto di Cloudflare sull'endpoint
`assets-upload-session` (HTTP 500, codice **10013**), tipico dei Worker già
esistenti. Classificato `not-in-wrangler` — non era un problema del progetto.

Prove che il progetto era pulito:
- asset: 40 file, ~1 MB, 0 symlink
- build locale OK

### Risoluzione

Con un token Cloudflare **account-scoped** valido, il deploy manuale è riuscito
al primo tentativo:

```bash
CLOUDFLARE_API_TOKEN=<token> \
CLOUDFLARE_ACCOUNT_ID=<account-id> \
npx wrangler deploy
```

Esito: `Uploaded skill-forge (7.51 sec)`.

### Verifica

| URL | Prima | Dopo |
|---|---|---|
| `skillforge.cc.cd/` | 200 | **200** |
| `skillforge.cc.cd/cli` | **404** | **200** |
| `/changelog`, `/marketplace` | — | 200 |
| `/admin` | — | 307 (redirect login, corretto) |

### Nota importante sul token

`/user/tokens/verify` restituisce **401** per i token account-scoped. **Non
significa che il token sia invalido.** Si verifica con `GET /accounts`.

### Sicurezza

Il token **non è mai stato messo su GitHub** (richiesta esplicita dell'utente):
- usato solo come variabile d'ambiente nel comando
- ripuliti i log di wrangler e i file in `/tmp`
- verificato con `grep`: nessuna traccia

## 2. Fix del dominio canonico nella CLI (pagina npm)

### Il problema segnalato

> "sulla pagina npm dà il link al worker.dev non a .cc.cd"

### Diagnosi

Non era solo un link. C'erano **due** punti sbagliati:

| File | Valore sbagliato |
|---|---|
| `cli/package.json` → `homepage` | `https://skill-forge.ciao22king.workers.dev` |
| `cli/src/config.ts` → `DEFAULT_URL` | stesso URL |

Il secondo è il più grave: **una install nuova parlava al host sbagliato**, anche
senza file di configurazione. npm mostra esattamente il campo `homepage`.

### Correzione

| File | Modifica |
|---|---|
| `cli/package.json` | `homepage` → `https://skillforge.cc.cd`, versione **0.1.1 → 0.1.2** |
| `cli/src/config.ts` | `DEFAULT_URL` → dominio canonico |
| `cli/README.md` | URL aggiornato |
| `cli/test/config.test.ts` | i test verificano il dominio canonico |
| `cli/package-lock.json` | versione allineata a 0.1.2 |

Verificato: **112 test CLI verdi**, `npm run build` rigenera `dist/` col dominio
giusto, `npm pack --dry-run` → homepage corretta.

Entrambi i domini servono la stessa API (`/api/marketplace` → 200 su entrambi),
quindi la correzione non rompe nulla.

Il **sito** (pagina `/cli`, `src/`) era **già corretto**: nessun riferimento a
`workers.dev` nel sorgente del sito.

### ⚠️ Attenzione

La pagina npm **non cambia** finché non si pubblica la `0.1.2`. Il codice è
pronto, ma npm mostra i metadati della versione *pubblicata*.

## 3. Errore `npm publish` "cannot publish over 0.1.1"

### Il messaggio

```
npm error You cannot publish over the previously published versions: 0.1.1.
```

anche dopo un `git pull`.

### Diagnosi

**Non è un problema di npm: è il branch.**

| Dove | Versione CLI |
|---|---|
| `main` (default) | 0.1.0 |
| `cloudflare-workers` | **0.1.2** ✅ |
| Copia locale dell'utente | **0.1.1** ← quella rifiutata |

La copia locale era `cloudflare-workers` **un commit indietro** (mancava il
commit del fix). Il `git pull` non aveva portato niente — quasi certamente
perché eseguito su `main`, o in un'altra cartella, o prima del push.

**Il messaggio di npm era corretto**: si stava tentando di ripubblicare la
`0.1.1` già online.

### Blocco successivo: modifiche locali

Il secondo tentativo ha dato:

```
error: Le tue modifiche locali ai seguenti file sarebbero sovrascritte:
    skill-forge/cli/package.json
```

Modifiche locali non committate bloccavano il fast-forward. È una **protezione
di git**, non un errore.

### Soluzione

```bash
cd skill-forge/cli
git diff package.json package-lock.json   # guarda prima cosa sono
git checkout -- package.json package-lock.json
cd ../..
git fetch origin
git switch cloudflare-workers
git pull --ff-only origin cloudflare-workers
```

**Verifica prima di pubblicare:**

```bash
cd skill-forge/cli
node -p "require('./package.json').version"   # DEVE stampare 0.1.2
npm publish
```

Se stampa `0.1.1`, **fermati**: sei sul branch o nella cartella sbagliata.

### Nota sulla pubblicazione npm

`npm publish` richiede il **login npm dell'utente** (l'agente non ha
credenziali in questo container: `npm whoami` → `ENEEDAUTH`).

Se compare l'`E403` sulla 2FA, serve un **granular access token con la casella
"Bypass two-factor authentication" spuntata alla creazione**. La spunta **non si
attiva dopo**: va fatta quando si crea il token.

## 4. Audit SEO: cosa era vero e cosa no

Un'AI ha dato tre raccomandazioni. Verificate una per una contro il codice reale.

### 4.1 "Solo 11 pagine trovate" — in parte vero

La sitemap live ha **19 URL**, non 11. Ma la sostanza era giusta: c'era spazio
per più contenuto indicizzabile. **Fatto.**

### 4.2 "Alt mancante su 5 pagine" — ❌ falso positivo

Tutte e 7 le `<img>` del sito hanno `alt=""` **di proposito**. Sono **avatar
accanto al nome del proprietario** → immagini decorative → `alt=""` è il markup
**corretto** (WAI/WCAG). Mettere un alt col nome avrebbe **peggiorato**
l'accessibilità (nome letto due volte dallo screen reader).

**NON corretto** — era la scelta giusta così com'era.

### 4.3 Ma l'audit ha mancato un bug vero

Il pulsante del **menu utente** (in alto a destra) non aveva **nessun nome
accessibile**: solo `aria-expanded` e `aria-haspopup`, con un `<img alt="">`
dentro. Uno screen reader annunciava solo *"button"*.

**Corretto**: aggiunto `aria-label="Account menu"`.

### 4.4 "Backlink / Linkscore" — ❌ non è codice

Nessuna modifica al repo può risolverla. È **outreach e partnership**: contattare
blog, community, progetti che citano strumenti simili. Lavoro di settimane.

### Cosa è stato fatto davvero

**5 nuove pagine indicizzabili**, una per use case:

| | |
|---|---|
| **Pagine** | `/use-cases/code-review`, `/incident-postmortem`, `/onboarding`, `/customer-support`, `/devops-runbook` |
| **Tipo** | Prerenderizzate (SSG) — servite istantanee, senza database |
| **SEO** | ognuna con `title`, `description`, `canonical`, OpenGraph, JSON-LD `Article` + breadcrumb |
| **Sitemap** | le 5 pagine aggiunte, **sempre presenti** anche se il DB è giù |
| **Linking** | `/use-cases` ora linka ogni pagina figlia (niente pagine orfane) |
| **llms.txt** | aggiornato con un link d'esempio |

Ogni pagina ha contenuto **unico e sostanziale**: la situazione, il materiale di
partenza, cosa fa la skill, i 5 passi che impone.

**Verifiche:** `tsc` pulito · **405 test verdi** (erano 400, +5 nuovi) ·
`npm run build` OK (le pagine compaiono come `● SSG`).

## 5. Il `robots.txt` e l'errore 1010

### L'affermazione dell'utente

> "il robots.txt blocca tutti"

### Verifica: FALSO

Il `robots.txt` **live** (non il codice):

```
User-Agent: *
Allow: /                    ← permette tutto
Disallow: /api/  /dashboard  /create/  /admin
```

**Nessun `Disallow: /`.** Anzi, c'è un blocco che *accoglie* i bot AI:

```
User-Agent: GPTBot
User-Agent: ClaudeBot
User-Agent: PerplexityBot
... (9 in totale)
Allow: /                    ← benvenuti
```

Controlli aggiuntivi, tutti negativi:

- ✅ `content-type: text/plain` corretto
- ✅ nessun BOM, nessun carattere invisibile
- ✅ nessun meta `noindex` (il sito ha `index, follow`)
- ✅ nessun header `X-Robots-Tag` sulle pagine pubbliche
- ✅ nessun `public/robots.txt` statico in conflitto
- ✅ `www` → 301 verso il dominio canonico

**Il `robots.txt` è a posto. Non è lui il problema.**

### ⚠️ Ma c'è un colpevole vero: `error code: 1010`

Testando con diversi user-agent:

| Client | Risposta |
|---|---|
| `curl`, browser, Googlebot, GPTBot, Ahrefs, Bingbot, ecc. | **200** ✅ |
| **`Python-urllib`** | **403** ❌ |

La pagina di errore dice: **`error code: 1010`**.

**`1010` è Cloudflare che blocca per "browser signature"** — una regola di
sicurezza che scatta **prima** che la richiesta raggiunga il Worker. Il
`robots.txt` non c'entra.

Questo spiega anche l'audit: lo strumento SEO probabilmente usa una libreria
HTTP (spesso Python) e ha ricevuto un 403. Da lì il "sembra bloccato".

### Cosa fare (in dashboard Cloudflare)

1. **Security → Bots**: se **Bot Fight Mode** è **ON**, spegnalo (causa più
   comune del `1010`).
2. **Security → WAF → Custom rules**: cerca regole che bloccano per user-agent o
   *browser integrity check*.
3. Preferisci una **allowlist mirata** a disattivare tutto.

### Onestà sulla gravità

Non c'è prova che Google sia bloccato: `Googlebot` e `GPTBot` ricevono **200**.
Il 403 colpisce solo `Python-urllib`. Rischio **medio**, non "letale".

Test definitivo: **Google Search Console → Controllo URL → "Visualizza come
Google"**. Se la pagina si carica, Google la vede.
